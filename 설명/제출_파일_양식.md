# 제출 레포 구성 가이드

> 이 문서는 **무엇을 어떻게 준비해야 점수가 제대로 나오는지**를 설명합니다.
> 서비스 이용 순서는 **사용방법.md**를 먼저 보세요.

---

## 1. 공통 규칙

| 항목 | 규칙 |
|------|------|
| 제출 방식 | **GitHub 공개 레포 주소 하나** |
| 공개 여부 | 반드시 **public**. 비공개 레포는 읽을 수 없습니다 |
| 기획서 | 레포 안에 `PLAN.md` 또는 `기획서.md` (자동 탐색) |
| 실행 코드 | 언어 무관. 앱 진입점이 있으면 우선 수집 |
| 같은 프로젝트 | 기획서와 코드가 **같은 과제**를 가리켜야 함 |

### 「같은 프로젝트」가 어긋나면 어떻게 되나요?

심사 시스템은 기획서와 코드의 **주제가 겹치는지** 먼저 확인합니다.
서로 다른 프로젝트를 가리키면 「의도 구현도」 분야가 부적격(0점) 처리되고,
결과서에 사유가 표시됩니다.

| 상황 | 결과 |
|------|------|
| 기획서는 회의실 예약, 코드는 쇼핑몰 | 의도 구현도 0점 + "주제가 일치하지 않습니다" |
| 기획서 파일이 레포에 없음 | **두 분야 모두 0점** |
| 코드가 없거나 소스로 볼 수 없음 | 심사 진행 불가 (오류 안내) |

## 2. 기획서

### 어디에 / 무엇을

레포 안에 아래 이름 중 하나로 두면 자동으로 찾습니다.

```
PLAN.md   기획서.md   planning.md   PLAN.txt   기획서.txt
```

- 하위 폴더도 탐색하지만 **루트에 가까울수록** 먼저 찾습니다.
- 파일이 여러 개면 위 목록의 앞쪽 이름이 우선입니다.

### 왜 필요한가요?

**두 심사 분야가 모두 기획서를 근거로 합니다.**

- 제1분야: 기획서만 읽고 문제 정의와 해결 방향을 평가
- 제2분야: 기획서와 코드를 **대조**해 의도대로 구현됐는지 평가

기획서가 없으면 대조할 기준이 없으므로 **전 항목 0점**입니다.

### 반드시 들어가면 좋은 내용

| 항목 | 왜 필요한가 |
|------|-------------|
| **목적·배경** | 어떤 문제를 왜 푸는지. 제1분야의 출발점 |
| **핵심 기능** | 번호를 매겨 구체적으로. 「핵심 요구사항 구현」의 대조 기준 |
| **성공 기준** | "무엇이 되면 성공인가". 「성공 기준 충족」이 이걸 봅니다 |
| **화면 구성** | 사용자가 보는 흐름 |
| **예외 처리** | 잘못된 입력·빈 파일 등을 어떻게 다루는지 |
| **범위 밖** | 이번에 만들지 않는 것. 「기획 의도 일치」에 유리 |

### 트랙별로 더 챙겨야 할 것

**기관용**이라면 —

- 공공 현장·민원·행정 절차에서 **무엇이 문제인지** 구체적으로
- 보안·개인정보·예산·조직·레거시 환경 등 **현장 적용 전제**

**기업용**이라면 —

- 업무 병목을 **시간·건수·금액으로 환산** (예: 주 3시간, 연 480만 원)
- **왜 직접 만들어야 하는지.** 엑셀·노션·기성 SaaS로 안 되는 이유를 밝히세요.
  이 항목(자체 구축 정당성)이 기업용에서 가장 크게 갈리는 지점입니다.
- 도입 비용·기존 시스템 연동·운영 인력

### 작성 예시 (목차)

```markdown
# [프로젝트 이름] — 기획서

## 1. 배경 — 어떤 업무가 왜 비효율적인가
   (기업용이라면 여기에 시간·건수·금액을 적으세요)

## 2. 왜 기성 도구로는 안 되는가
   (기업용 필수. 검토한 대안과 배제 사유를 표로)

## 3. 핵심 기능
   1) ...
   2) ...

## 4. 성공 기준
   - ... 하면 성공이다

## 5. 화면 구성

## 6. 예외 처리

## 7. 도입·운영
   (배포 위치, 데이터 확보 경로, 유지보수 담당)

## 8. 범위 밖
```

### 흔한 실수와 결과

| 실수 | 결과 |
|------|------|
| "업무 효율을 개선한다"만 적음 | 문제·비용 구체성 / 페인포인트 명확성 하락 |
| 기능을 10개 적고 코드엔 3개만 구현 | 핵심 요구사항 구현 크게 하락 |
| 성공 기준 없음 | 성공 기준 충족 판단 불가 → 하락 |
| 기성 도구 대안 검토 없음 (기업용) | **자체 구축 정당성 20~50점대** |
| 기획서 파일명이 `제안서.md` | 자동 탐색 실패 → **전 항목 0점** |

## 3. 실행 코드

### 어디에 / 무엇을

레포에 그대로 두면 됩니다. 심사 시스템이 알아서 수집합니다.

- **언어 무관**: `.py .js .jsx .ts .tsx .html .css .java .kt .go .rs .rb .php .c .cpp .cs .swift .sql .sh .vue .svelte`
- **우선 수집**: `app.py` `main.py` `streamlit_app.py` `index.html` `app.js` `server.js`
  `package.json` `requirements.txt` 등 진입점·매니페스트
- **자동 제외**: `node_modules` `.venv` `__pycache__` `dist` `build`,
  잠금 파일(`package-lock.json` 등), 압축본(`*.min.js`)
- **수집 한도**: 최대 25개 파일

### 왜 여러 파일을 다 읽나요?

기획서에 적은 기능이 여러 파일에 나뉘어 있어도 찾아내기 위해서입니다.
파일을 억지로 하나로 합칠 필요는 없습니다.

### 흔한 실수와 결과

| 실수 | 결과 |
|------|------|
| 레포가 비공개 | 심사 불가 — "공개 레포인지 확인해 주세요" |
| 소스 파일이 없음 (문서만 있는 레포) | 심사 불가 — "실행 코드를 찾을 수 없습니다" |
| 기획서에 없는 기능을 코드에 잔뜩 추가 | 기획 의도 일치 하락 |
| 코드가 기획서와 다른 주제 | 의도 구현도 0점 |

> **참고**: 모듈 분리, 예외 처리, 설정 파일 같은 **합리적인 구현상 보완**은
> 감점 사유가 아닙니다. 감점은 기획 핵심을 훼손했거나 무관한 기능을 과도하게
> 넣은 경우에만 적용됩니다.

## 4. README는 어떻게 하나요?

**채점 대상이 아닙니다.** 있어도 되고 없어도 되며 점수에 영향을 주지 않습니다.

다만 다른 사람이 프로젝트를 이해하고 실행하려면 여전히 필요하므로,
협업·제출 관행 차원에서 쓰는 것은 권장합니다.

---

## 5. 제출 전 체크리스트

- [ ] 레포가 **public**으로 되어 있다
- [ ] `PLAN.md` 또는 `기획서.md`가 레포에 있다
- [ ] 기획서에 **핵심 기능**과 **성공 기준**이 적혀 있다
- [ ] (기업용) 문제 규모를 **숫자로** 적었다
- [ ] (기업용) **기성 도구 대신 직접 만드는 이유**를 적었다
- [ ] 기획서와 코드가 **같은 프로젝트**다
- [ ] 앱 진입점 파일이 레포에 있다
- [ ] 접수 화면에서 **트랙을 올바르게** 선택했다
